# Phase 1 — core + HR

The build guide for the first pilot: the shared `core` tables, the approval engine every
later pilot reuses, the HR module, three security roles and the HR Power BI dashboard.

Dressed for **Woodgrove Advisory**, the fictional accounting firm, on the `accounting-firm`
profile. Phase 1 builds against `hr-starter` (`core` + `hr`) first, because the industry
overlay only adds columns and reference data on top — see [§8](#8-moving-to-the-accounting-firm-profile).

## 2. Build order

Run from the repository root. Everything is derived from the YAML, so this sequence is
repeatable into an empty environment.

```bash
pip install -r tools/requirements.txt
```

```bash
python tools/schematool.py validate && python tools/schematool.py docs --check
```

```bash
python tools/ppcheck.py
```

```bash
python tools/schematool.py export --profile hr-starter
```

```bash
python tools/dvgen.py --profile hr-starter --prefix wga --layers core,hr --solution WoodgroveHR
```

```bash
python tools/dvdeploy.py --plan build/dataverse/hr-starter --dry-run
```

```bash
python tools/dvdeploy.py --plan build/dataverse/hr-starter --url https://<env>.crm11.dynamics.com --solution WoodgroveHR
```

```bash
python tools/secgen.py --profile hr-starter --prefix wga --strict
```

```bash
python tools/pbigen.py --profile hr-starter --prefix wga --strict
```

```bash
python tools/demodata.py --profile hr-starter --people 64
```

`ppcheck` comes before anything that writes, so a missing consent or an expired secret is
found in ten seconds rather than halfway through a 634-component import.

### Why the components go in this order

`dvgen` writes a plan in five steps, and the order removes a whole class of failure:

1. **global choice sets** — a column cannot bind to an option set that does not exist
2. **tables**, each with only its primary name column
3. **columns** — every non-relationship column
4. **relationships** — lookups, parents, then many-to-many
5. **alternate keys** — once the columns they cover exist

Creating *all* tables before *any* lookup means tables that reference each other need no
topological sort. `Employee.manager` points at `Employee`; `OrgUnit.parentOrgUnit` points at
`OrgUnit`; `Position.reportsTo` points at `Position`. Sorting those is impossible, so the
plan sidesteps it.

Every step is idempotent — an existing component is reported and skipped — so a run that
fails on component 400 can simply be run again.

### The three "regarding" columns

`ApprovalRequest`, `DocumentReference` and `Comment` each point at *any* record. The data
dictionary maps that to **two text columns** — "Text ×2 (table name + id)" — rather than a
Dataverse polymorphic lookup, so `dvgen` generates them like any other column:

| Table | Columns generated |
|---|---|
| `ApprovalRequest` | `wga_regardingtable` (100) + `wga_regardingid` (36) |
| `DocumentReference` | the same pair |
| `Comment` | the same pair |

That is the right trade, not a shortcut. A real multi-table lookup has to **enumerate its
targets** at creation, so adding the Travel or CRM pilot later would mean altering the
relationship on a table that already holds data. The text pair points at anything, including
tables that do not exist yet — which is what a shared approval engine needs.

The cost is that Dataverse will not join on it for you. The app and the flow resolve the pair
themselves, and a model-driven form shows it through a quick-view or an embedded canvas app
rather than a native lookup control. Write the table name as the **logical** name
(`wga_leaverequest`), not the display name, or nothing will resolve.

There are no manual metadata steps left: `dvgen` reports zero, and `dvdeploy` prints any that
appear if the schema later gains a construct the API cannot create.

## 3. Security

### 3.1 Three personas

| Role | Who has it | Shape of access |
|---|---|---|
| **HR – Employee Self-Service** | everyone, via an Entra group | reads the directory and reference data; owns their own leave, training, skills, personal details and onboarding tasks |
| **HR – People Manager** | anyone with direct reports, *in addition to* the employee role | their team's HR records at business-unit depth, and leave approval |
| **HR – Administrator** | a small named group, reviewed quarterly | the employee lifecycle at parent-child depth; owns HR reference data and approval policies |

The matrix is generated, not written: `build/dataverse/hr-starter/security/matrix.md`. It
has one row per table and one column per role, so it cannot drift from the schema.

### 3.2 Business units

One root business unit for the firm, one child per legal entity.

- HR generalists sit in the **root**, so `parentChild` (Deep) depth reaches every entity.
- Managers sit with **their own** legal entity, so `businessUnit` (Local) depth stops at it.

This is what makes the HR role `parentChild` rather than `organization`: a federated firm
can keep one legal entity's HR data away from another's HR team by moving them into child
units, with no change to the roles.

**Dataverse depth cannot express "my direct reports".** There is no "rows where I am the
manager" depth. So the manager role grants business-unit depth and the model-driven app's
views filter to `JobAssignment.manager = current user`. Treat the role as the floor and the
views as the working scope — and say so in the case study, because it is the honest
limitation of the platform rather than of the design. Where a hard boundary is needed
instead of a tidy default view, the alternatives are a business unit per team (unwieldy) or
row-level sharing driven by a flow (more moving parts); neither is worth it for Phase 1.

### 3.3 Why compensation needs three controls

The exit criterion is "compensation invisible to non-HR". One control is not enough,
because each covers a different route to the data:

| Route to the data | Control |
|---|---|
| The HR app, or any Dataverse query | `Compensation` is user-owned, and the employee and manager roles grant `read` at **Basic** depth only. A manager reads their own salary history and no one else's — not even a direct report's. `Offer` and `Grade` are closed to both roles entirely. |
| The Power BI dashboard | `Compensation` is **not in the dataset at all**, and no measure mentions it. A dataset is a copy of the data under its own permissions, so a role in Dataverse does not protect a table once it has been imported. Pay reporting gets its own workspace and dataset for the reward team, which is Phase 6. |
| A later edit to either | `tests/test_secgen.py` asserts the manager's grant on `Compensation` is exactly `{read: user}` and that `Offer` and `Grade` are absent; `tests/test_pbigen.py` asserts `Compensation` is not in the dataset and appears in no measure. Both fail the build if someone widens them. |

The generator enforces the reasoning behind this. **Column security applies only where a
column is classified more strictly than its table.** A wholly restricted table is protected
by security roles, which is cheaper to run than field security on every column. In core + HR
that leaves four secured columns rather than twenty-six:

| Column | Table's classification | Why the column is stricter |
|---|---|---|
| `Employee.mobilePhone` | internal | a personal number on an otherwise firm-wide directory |
| `EmployeeCredential.credentialNumber` | internal | a practising certificate number is identifying |
| `JobRequisition.salaryMin` | internal | pay range on a table hiring managers need |
| `JobRequisition.salaryMax` | internal | as above |

`Compensation.amount` is *not* on this list, and should not be: the whole table is
restricted, so the role does the work.

### 3.4 Auditing

`dvgen` turns on table auditing wherever the schema marks a table `confidential` or
`restricted` — 12 of the 50 tables in Phase 1, including `Compensation`,
`EmployeePersonalDetails`, `Offer`, `PerformanceReview`, `LeaveRequest` and `Candidate`.
Enable auditing at the environment level too, or the table setting does nothing.

## 4. The approval engine

Build this **once**. Travel, expenses, timesheets and pay changes all reuse it; it is the
single highest-leverage thing in Phase 1.

### 4.1 How a chain is chosen

```
ApprovalPolicy          which chain applies: entity + legal entity + org unit + amount band
  └── ApprovalPolicyStep    the steps, in sequence
ApprovalRequest         one run against one record
  └── ApprovalStep          one task for one approver
```

`ApprovalPolicy.appliesToEntity` holds the table's logical name. Policies are tried in
`evaluationOrder` and the first match wins, so put the most specific first: a policy with a
`legalEntity` and an `orgUnit` before the firm-wide fallback. Always keep a catch-all policy
with no filters and the highest `evaluationOrder`, or a record in a new org unit will have
no chain and sit in `draft` forever.

### 4.2 Resolving an approver

`ApprovalPolicyStep.approverType` is the only part with real logic:

| `approverType` | Resolves to | Reads |
|---|---|---|
| `manager` | the requester's line manager | `JobAssignment.manager` on the current primary assignment |
| `skipLevelManager` | that manager's manager | the same, applied twice |
| `specificEmployee` | a named person | `approver` |
| `orgUnitHead` | the head of their department | `OrgUnit.head` |
| `costCenterOwner` | whoever owns the budget | `CostCenter.budgetOwner` |
| `recordField` | a person named on the record itself | `approverField` holds the column name |
| `group` | an Entra group — any member may act | `approverGroupId` |

Resolution reads the **current** assignment: the `JobAssignment` row whose `validFrom` has
passed and whose `validTo` is empty. Three cases to handle explicitly, because each is a
real support ticket:

- **No manager** (the managing partner). Skip to the next step, or fall back to
  `orgUnitHead`. Never leave the step unassigned.
- **The approver is the requester.** Skip the step. A partner approving their own leave
  passes an audit badly.
- **The approver has left.** `EmploymentStatus` is `leaver`, so resolve to their manager
  instead, and reassign anything already pending.

`completionRule` is `anyApprover` or `allApprovers`. With `allApprovers`, the request moves
on only when every step at that sequence is approved; one rejection ends the whole request.

### 4.3 Timeouts

`reminderAfterHours` and `escalateAfterHours` on the policy, `timeoutHours` on the step.
Drive them from a scheduled flow rather than a per-request delay: a flow waiting on a delay
for three days is a flow that breaks when the environment is updated. The
`Avg Leave Approval Hours` and `Approvals Overdue` measures make the result visible, which
is how you find out whether the policy's numbers were sensible.

### 4.4 Writing the outcome back

The record keeps a lookup to its latest request (`LeaveRequest.approvalRequest`,
`Compensation.approvalRequest`, and so on). On completion the flow sets:

- `ApprovalRequest.status` → `approved` / `rejected`, `completedOn`, `outcomeComments`
- the record's own status — `LeaveRequest.status` → `approved` or `rejected`
- for approved leave: `LeaveBalance.pending` down, `LeaveBalance.taken` up

Store the flow run id in `ApprovalRequest.flowRunId`. When someone asks why a request stalled
in March, that column is the difference between an answer and a shrug.

## 5. Joiner, mover, leaver

### 5.1 The effective-dated spine

Three tables carry a person's history, and the distinction matters:

| Table | Grain | A new row when |
|---|---|---|
| `Employment` | one contract with one legal entity | they join, or rejoin after leaving |
| `JobAssignment` | job, reporting line, location, FTE | any of those change — promotion, transfer, manager change |
| `Compensation` | base pay | pay changes |

`JobAssignment` is effective-dated: the row with no `validTo` is current, and it is projected
onto the `Employee` directory record so the firm-wide directory stays simple. A promotion
**closes** the old row with a `validTo` and opens a new one — it never edits in place. That
is what lets the dashboard answer "what was headcount last March" correctly, and it is why
`Headcount` filters on `validFrom`/`validTo` rather than counting `Employee` rows.

A rehire creates a *second* `Employment`, which is why `continuousServiceDate` exists
separately from `startDate`: statutory entitlements follow continuous service, not the
latest contract.

### 5.2 Leave request end to end

The exit criterion. Each step with the record state after it:

| # | Step | After it |
|---|---|---|
| 1 | Employee opens self-service, picks a leave type | — |
| 2 | App shows `LeaveBalance.available` for the current leave year | — |
| 3 | They pick dates; the app computes `duration` from the working pattern, `HolidayCalendar` and the half-day flags | — |
| 4 | Policy checks run: `minNoticeDays`, `allowNegativeBalance`, `requiresAttachmentAfterDays` | blocked, or warned with a reason |
| 5 | They submit | `status` = `submitted`, `submittedOn` set, `LeaveBalance.pending` up |
| 6 | Flow finds the `ApprovalPolicy` for `wga_leaverequest` and creates an `ApprovalRequest` | `status` = `pending` |
| 7 | It creates `ApprovalStep` rows and resolves approvers ([§4.2](#42-resolving-an-approver)) | first step `pending`, rest `waiting` |
| 8 | The manager is notified and approves in Teams or the app | step `approved` |
| 9 | Last step done → the request completes | request `approved`, `completedOn` set |
| 10 | Flow writes back | `LeaveRequest.status` = `approved`, `pending` down, `taken` up |
| 11 | The leave appears on the team calendar and in the dashboard | `Leave Days Taken` moves |

Demonstrate the **rejection** path too, and one **out-of-policy** request that is submitted
with a warning and approved anyway. A demo where everything succeeds proves far less than
one where a rule fires.

### 5.3 Onboarding

`ChecklistTemplate` + `ChecklistTemplateTask` → `EmployeeChecklist` +
`EmployeeChecklistTask`. One template per `ChecklistType` (onboarding, offboarding, a role
change). Each template task names a `ChecklistAssigneeRole` — the new joiner, their manager,
HR, IT, facilities — and the flow resolves it to a person when it instantiates the checklist,
the same resolution the approval engine uses.

Trigger it when an `Employment` row is created with a future `startDate`, not on the start
date itself: laptops take time.

For Woodgrove, the onboarding template must create the `EmployeeCredential` rows for a new
joiner's practising certificates, because [§7](#7-the-dashboard) counts anyone without them
as non-compliant from day one.

## 6. The apps

### 6.1 HR model-driven app (HR administrators)

Site map by lifecycle rather than by table — HR thinks in processes:

| Area | Tables |
|---|---|
| People | Employee, Employment, JobAssignment, EmployeePersonalDetails, EmergencyContact |
| Reward | Compensation, Grade *(restricted to the reward column profile)* |
| Absence | LeaveRequest, LeaveBalance, LeavePolicy, LeaveType |
| Hiring | JobRequisition, Candidate, JobApplication, Interview, InterviewFeedback, Offer |
| Development | PerformanceReview, Goal, ReviewCycle, EmployeeSkill, TrainingRecord |
| Compliance | EmployeeCredential, CredentialType, TrainingCourse |
| Setup | JobFamily, JobProfile, Position, ChecklistTemplate, ApprovalPolicy |

Use a business process flow on `PerformanceReview` to lock the self-assessment once the
manager's section opens. The employee role grants `write` on their own review, so the stage
gate — not the role — is what stops them editing it after submission.

### 6.2 Employee self-service canvas app (in Teams)

Four screens: **My leave** (balance, request, history), **My profile** (personal details,
emergency contacts), **My development** (training, skills, credentials, CPE progress), **My
approvals** (what is waiting on me).

Everything it touches is at Basic depth, so the app sees only the signed-in user's rows with
no filtering in the app itself — the role does it. The one thing to get right is the CPE
progress bar: an accountant wants to know how many hours they still owe before the deadline,
not a percentage.

### 6.3 Accessibility

Keyboard reachable, labels on every control, contrast checked, and usable on a phone — the
self-service app will mostly be opened on one. This is an exit criterion for every pilot,
so build it in rather than retrofitting.

## 7. The dashboard

27 measures over 25 tables, four pages: Overview, Leave, Compliance, Recruitment. Built from
[`powerbi/hr-dashboard.yaml`](../powerbi/hr-dashboard.yaml); every DAX reference is checked
against the generated model, so a renamed column fails the build rather than the refresh.

**Compliance is on the first page, not buried.** For an audit firm a lapsed practising
certificate is a client-facing risk, so `CPE Compliance %` and `Credentials Expiring 90 Days`
sit beside headcount. That is the industry flavour of this pilot showing up in the report
layout rather than only in the labels.

Measures worth knowing about:

- **`Headcount`** counts distinct people with a current *primary* assignment, so a secondment
  does not count twice.
- **`Attrition %`** is rolling twelve months over average headcount, so it does not reset
  each April and does not divide by a single month's figure.
- **`Leave Liability (Days)`** reads `LeaveBalance`, not `LeaveRequest` — finance needs
  accrued-but-untaken, which is a balance, not a sum of requests.
- **`CPE Compliance %`** caps each person at their own requirement, so someone far over
  target cannot mask a colleague who is short.
- **`Avg Leave Approval Hours`** is the service level for [§5.2](#52-leave-request-end-to-end),
  and the reason the approval engine records `assignedOn` and `decidedOn`.

Nine relationships are inactive role-playing paths — `LeaveRequest.coverBy`,
`JobAssignment.manager`, `PerformanceReview.reviewer`, and so on. Only one path between a
pair of tables may be active, and the active one is always the business subject of the row
(`LeaveRequest.employee`). Reach the others with `USERELATIONSHIP`.

The report canvas is laid out by hand in Desktop from the generated `pages.md`, then the
saved `.Report` folder is committed. Everything else about the report is generated.

## 8. Moving to the accounting-firm profile

Phase 1 builds `hr-starter`. The `accounting-firm` profile adds `proserv-compliance` and the
`accounting-*` overlays, which **only add** columns, tables and reference data — nothing is
edited or removed, so the move is additive:

```bash
python tools/schematool.py export --profile accounting-firm
```

```bash
python tools/dvgen.py --profile accounting-firm --prefix wga --layers accounting-hr,proserv-compliance --solution WoodgroveHROverlay
```

Putting the overlay in its **own solution** is what keeps upgrades safe: the base solution
can be reimported without overwriting the overlay, which is the Dataverse layering model
doing the work the schema principles promised.

Then rerun `secgen` and `pbigen` against the new profile. Both will report any new table no
role can reach — which is exactly the review you want when an overlay lands.

## 9. Demo data

`tools/demodata.py` builds Woodgrove Advisory: 64 staff across Audit, Tax, Advisory,
Bookkeeping and three support functions, in London and Manchester, with assignment and pay
history, leave, approvals, credentials, training, reviews and an open recruitment pipeline —
around 1,800 rows over 31 tables.

It is **deterministic**: the same `--seed` gives the same firm, so a demo can be rebuilt and
the screenshots still match.

Every row is checked against the resolved model before anything is written — required columns
present, choice values real enum keys, lookups resolving to a row that exists in the data or
in the schema's seeds — plus four invariants that come from the model rather than the code:

- exactly one `JobAssignment` with no `validTo` per active person, and a contiguous history
  where each closed row ends where the next begins
- no leave request outside its balance period, and none ending before it starts
- no balance overdrawn on a leave type whose `allowNegativeBalance` is false
- no approval step assigned to the person who raised it

Writing these checks found four real problems in the first pass: `Candidate.retainUntil` was
missing (a required GDPR field), `ChecklistTemplateTask` uses `title`/`dueOffsetDays` rather
than `name`/`dueDayOffset`, `Holiday` uses `holidayDate`, and sixteen people were overdrawn
on annual leave.

The data is shaped so **no dashboard tile reads zero**, which a random generator will
otherwise do on a firm this size: the credential watchlist is topped up to at least four
expiring and two expired, and mandatory training is due on each person's joining
anniversary so some of the firm is always overdue. `manifest.json` carries a `loadOrder`
with lookup targets before their referrers.

The output is JSON per table with lookups written as the target's natural key — the same
convention `schemas/*.yaml` uses for `seed:` — so reference data and demo data load through
one code path.

## 10. Open decisions this phase needs

The roadmap's §9 decisions, narrowed to the ones that block Phase 1:

1. **Publisher prefix.** The tools default to `wga` (Woodgrove Advisory) in every example
   here. It is in every table name and hard to change later, so settle it before the first
   `dvdeploy` run.
2. **Solution names.** `WoodgroveHR` for the base, `WoodgroveHROverlay` for the industry
   overlay. Decide now, since components land in whichever solution is named at creation.
3. **Business unit layout.** [§3.2](#32-business-units) assumes one child per legal entity.
   If Woodgrove is a single legal entity, the HR role's `parentChild` depth behaves exactly
   like `organization` and the distinction costs nothing — but make it a decision rather
   than an accident.
4. **Leave year.** The schema supports `yearStartMonth` per policy. The dashboard's date
   table assumes a 31 March year end; if the leave year is the calendar year instead, change
   `dateTable.yearEndMonth` in the dashboard YAML.
5. **Privacy law.** `EmployeePersonalDetails` holds `nationalIdReference` and
   `dateOfBirth`. Under UK GDPR these need a retention period and a lawful basis recorded
   before any real data goes near the tenant. The demo tenant holds fictional data only,
   which is the point of keeping client data out of it.
